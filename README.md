# Audit Evidence Graph + Tie-Out Workbench

[Live demo](https://audit-evidence-graph.vercel.app) · [GitHub repository](https://github.com/imranrkhan13/audit-evidence-graph)

Demo login: **auditor / auditor123**. Hosted changes are temporary.

A candidate-project demo built for the Modus MTS role. It shows how financial
assertions can be traced to source evidence, reconciled against ledgers and
related documents, routed to human review, and exported with a complete
audit trail.

## ⚠️ Important — read before anything else

**This is a synthetic demo.** Every document, invoice, vendor, ledger row,
and bank transaction in this system is fixture data generated by
`backend/app/seed.py` for demonstration purposes.

This project does **not**:
- integrate with Modus's real product or infrastructure in any way
- use real accounting-firm or client data
- represent real production audit outcomes
- implement anything beyond what's described in this README

Every seeded document is labeled `[SYNTHETIC FIXTURE DOCUMENT]` in its text,
and every export includes an explicit synthetic-data disclaimer.

## What this demonstrates

1. Ingesting documents (invoices, approvals, bank statements, a general
   ledger) with content hashing and page-level storage.
2. Extracting strict typed fields via a fixture extraction provider sitting
   behind a clean adapter interface — a real LLM-backed provider could be
   swapped in without touching anything downstream.
3. Normalizing invoice IDs, vendors, currencies, dates, and amounts with
   pure, testable Python functions.
4. Running a **fully deterministic** tie-out rule engine — no model ever
   decides whether numbers reconcile. (Vector/semantic search, if added,
   would only ever help *locate* evidence, never decide pass/fail.)
5. Routing low-confidence, contradictory, or materially exceptional
   assertions to a human review queue with approve/reject/request-evidence
   actions.
6. Recording every step — extraction, normalization, tie-out, rerun, review,
   approval, export — as an **append-only** audit event.
7. Handling document amendments: a new version is created, the old version
   is preserved (never deleted), and only the assertions actually affected
   are rerun, with prior tie-out results kept in history.
8. Exporting an evidence-linked, auditor-ready JSON payload and a printable
   HTML report.

## Hosted free demo (Vercel)

The repository includes `vercel.json` and `api/index.py` to deploy the React
frontend and Python backend together. Set a freshly generated `SECRET_KEY` in
Vercel before deploying. Never reuse or publish the local `.env` file.

This hosting mode uses temporary SQLite storage containing only generated
sample data. Each server instance has its own copy; changes can disappear on
restart or when a request reaches a different instance. Download reports to
keep a copy. Seeded record IDs are stable across instances so sign-ins and
links to the original sample records remain valid. New records and edits are
not durable. Demo accounts are shared and are not suitable for private data.

The Docker setup remains available for local use with PostgreSQL. The hosted
entrypoint never connects to that database. For durable hosted storage, use a
managed database and a non-destructive initialization workflow instead.

Deploy from the repository root with `vercel --prod`, or import the repository
into Vercel using the included configuration. The frontend displays the hosted
demo notice only when built with `VITE_HOSTED_DEMO=true`.

## Architecture

```
backend/   FastAPI + SQLAlchemy + Pydantic, SQLite (dev) or PostgreSQL (docker-compose)
  app/
    models.py         13-table data model (see below)
    tie_out.py         pure deterministic rule functions
    engine.py           orchestrates rules -> TieOutResult rows -> assertion status -> ReviewTask
    normalization.py    pure normalization functions (invoice id, vendor, currency, date, amount)
    extraction/
      provider.py        abstract ExtractionProvider interface
      fixture_provider.py  synthetic, deterministic implementation
    seed.py              generates all synthetic fixtures + runs the initial tie-out
    routers/             auth, engagements, assertions, documents, review, audit, export
  tests/                 35 pytest tests

frontend/  React + TypeScript + Vite + Tailwind
  src/pages/    Dashboard, AssertionsList, AssertionDetail, ReviewQueue,
                DocumentViewer, AuditTimeline, Export, Login
```

### Data model

`engagements`, `documents`, `document_pages`, `extracted_entities`,
`assertions`, `ledger_entries`, `evidence_links`, `tie_out_runs`,
`tie_out_results`, `review_tasks`, `approvals`, `workflow_runs`,
`audit_events`, plus `users` for local auth/RBAC.

### Data flow (one assertion's life)

1. `seed.py` creates a synthetic invoice document + page, registers its
   fixture extraction fields (`invoice_id`, `vendor`, `amount`, `date`,
   `currency`), and writes `ExtractedEntity` rows.
2. A ledger row and (usually) a bank-statement line and approval memo are
   created alongside it.
3. An `Assertion` row is created (e.g. "Invoice INV-2025-1015 ... ties out
   to the general ledger and bank records").
4. `EvidenceLink` rows tie the assertion to its source document, the ledger
   document, and the bank statement.
5. `engine.run_tie_out_for_assertion()` runs the deterministic rules in
   `tie_out.py`, writes one `TieOutResult` row per rule, and sets the
   assertion's final `status` (`pass` / `needs_review` / `fail`).
6. If the assertion needs review, a `ReviewTask` is opened with a reason,
   financial impact, and risk level.
7. Every step above also writes an `AuditEvent` row. Nothing is ever
   updated or deleted from `audit_events`.
8. If the source invoice is later amended (`POST /documents/{id}/amend`),
   a new document version is created, the old one is marked superseded
   (not deleted), and **only** assertions whose `subject_key` matches that
   invoice are rerun — their prior `TieOutResult` rows are marked
   `is_current=False` rather than being overwritten.

### Roles

- **Admin** — full access, including amending documents.
- **Auditor** — full read access, can amend documents, can view (but not
  act on) the review queue.
- **Reviewer** — can act on review tasks (approve / reject / request
  evidence); cannot amend documents.

## Setup

### Option A — Docker Compose (recommended)

```bash
docker compose up --build
```

This starts PostgreSQL, seeds it automatically, starts the FastAPI backend
on `http://localhost:8000`, and serves the built frontend (via nginx,
proxying `/api` to the backend) on `http://localhost:5173`.

> Note: the Docker images were written following standard multi-stage
> Python-slim and Node-slim/nginx patterns, but Docker was not available in
> the sandbox this project was built in, so `docker compose up` itself was
> not run end-to-end here. The backend and frontend were each verified
> independently outside Docker (see BUILD_STATUS.md) — if `docker compose
> up` surfaces anything, it's most likely one of the environment-specific
> Dockerfile details rather than the application code itself.

### Option B — Run locally without Docker

**Backend**
```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL="sqlite:///./audit_demo.db"   # or a postgres URL
python -c "from app.seed import run_seed; run_seed()"
uvicorn app.main:app --reload --port 8000
```

**Frontend**
```bash
cd frontend
npm install
npm run dev   # http://localhost:5173, proxies /api to :8000
```

## Seeded scenario

Exactly 20 assertions, matching a fixed, reproducible plan in
`backend/app/seed.py`:
- **14 pass** automatically (extraction confident, invoice = ledger = bank
  transaction, approval present, payment date in period).
- **3 need review** because their extracted amount's confidence is below
  0.85 (0.58, 0.72, 0.80) — even though the numbers happen to reconcile,
  low confidence always forces human review; low confidence can never
  auto-resolve to "pass".
- **2 fail** because the invoice total and the ledger amount genuinely
  differ (a $250.00 and a -$75.50 discrepancy).
- **1 fails** because no invoice document was ever ingested for a ledger
  reference — a missing-evidence case.

## Limitations

- The extraction "provider" is a fixture — it returns pre-baked values keyed
  to each synthetic document. No LLM or OCR model runs in this project. The
  `ExtractionProvider` interface exists specifically so a real provider
  could be substituted later.
- Vector/semantic search for evidence location is not implemented in this
  demo; the spec asked for it to be optional and to never influence tie-out
  decisions, so it was left out in favor of spending the time budget on the
  deterministic engine, RBAC, versioning/rerun, and test coverage.
- Currency conversion uses a small fixed synthetic FX table, not a live
  rate feed.
- The document viewer renders extracted text as plain text, not real PDF
  rendering — there is no actual PDF generation or parsing in this system.
- `docker compose up` was not executed in the environment this was built
  in (no Docker daemon available); see the Setup note above.
- Duplicate-invoice detection, line-item-sum checks, and identity-match
  checks are all implemented and unit-tested, but the 20 seeded assertions
  don't include a duplicate-invoice-number scenario by design, since the
  brief specified an exact 14/3/2/1 breakdown with only two documented
  exception categories (mismatch, missing evidence). The duplicate check
  is proven by direct unit tests in `tests/test_tie_out.py`.

## Feature addition: Continuous Risk Monitoring + Evidence Search

Added after researching Modus's own public statements (funding-round press
coverage, their AI-product profile, and the exact job posting for this
role) rather than guessing. Three sources converged on the same theme:

- Modus's own funding coverage: *"the system also supports continuous
  monitoring of financial data, a meaningful departure from the
  traditional model of periodic, sample-based testing... auditors can
  surface anomalies in near real time and allocate their judgment to the
  areas that carry the most risk."*
- Their product profile: *"AI review assistants... trained on
  partner-specific standards to flag anomalies..."*
- The MTS job posting itself: *"cross-check financials... Python backends
  **and vector stores**..."*

**What was built:**
- `backend/app/anomaly.py` — a deterministic, explainable statistical
  risk-scoring module (leave-one-out z-score per vendor, round-number
  amounts, near-approval-threshold amounts, weekend postings, first-time
  vendors). Every ledger entry in the engagement is scored right now, not
  sampled — the literal mechanism behind "continuous monitoring."
- `backend/app/search.py` — a from-scratch TF-IDF vector search over every
  document page (the "vector store" the job posting asks about),
  explicitly walled off from `tie_out.py`/`engine.py` so it can only help
  a human *find* evidence faster, never decide a tie-out. That boundary is
  covered by a test, not just a comment.
- `GET /risk/radar` and `GET /evidence/search` endpoints, plus a new
  **Risk Radar** page in the frontend (ranked anomalies with plain-English
  reasons, deep-linking to the underlying assertion, and a live evidence
  search box).
- 13 new tests (`test_anomaly.py`, `test_search.py`, plus two new API
  tests), all passing alongside the original 35 — **48/48 total**.

This keeps the app's core guarantee intact while adding the one thing the
research pointed to: AI/statistics can rank where attention should go and
help find things faster, but a deterministic rule (or a human) still makes
every actual conclusion.

## New: Evidence Change Impact + landing page

The root route `/` now presents a responsive Modus-inspired product concept.
`/change-impact` opens an authenticated, read-only dependency workbench. Its
source selector covers all current engagement documents, including shared
ledgers and bank statements. Invoice previews compare a proposed total with
one unambiguous USD ledger row, while preserving all existing conclusions.
Reports include current-rule scope, prior approvals and stale version links,
and can be downloaded as JSON. See [RESEARCH.md](RESEARCH.md) for the source
matrix, opportunity rationale, and limits of public feature-gap research.

API: `GET /impact/documents?engagement_id=...` and
`GET /impact/{document_id}?proposed_amount=...`. Both require authentication.
This feature adds no database tables or migrations and never writes to the
engagement. It does not automatically rerun checks or revoke approvals.

## Signing in and learning the app

Open `/login` and use **auditor / auditor123** to explore the demo. These
values are filled in already. Use **reviewer / reviewer123** for review
buttons, or **admin / admin123** for all demo actions.

`POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` are database settings.
`SECRET_KEY` is used by the server to protect sign-in tokens. They are not
credentials for the app's login form.

A sign-in lasts eight hours. If it expires or the server rejects it, the app
clears the old session and asks you to sign in again, then returns you to the
page you were using. Existing saved audit data is unaffected. Report downloads
now send the same authentication as other app requests.

Visit `/guide` for a plain-language walkthrough, a worked example, and a glossary.
Run the frontend authentication regression tests with `cd frontend && npm test`.
